Trading Dashboard 7-Day Build

The dashboard today streams made-up ticks through one Python process and sends every tick to every browser. Over seven focused days, one developer rebuilds it around live exchange feeds, a C++ order book, a message bus and a conflating gateway, and proves every gain with benchmarks. Each day ships a few feature branches, merged one lane at a time through CI.

Architecture

From one busy process to a pipeline

Dots are messages. Their density follows the real message rate on a cube-root scale, so 10,000 per second still fits on screen. Red dots reach a browser that throws them away.

Life of a tick

Eight hops from the exchange to your screen

Step through one order-book update after the upgrade. Every hop that crosses a process boundary stamps a timestamp, which is how Day 7 measures latency per hop.

    Order book sync

    Keep a local book correct, and notice when it isn't

    Exchanges send a snapshot, then numbered changes. If one change goes missing, the next number skips and the checksum stops matching, so the client throws the book away and rebuilds it. Drop a delta to watch it happen.

      stateDiagram-v2
  [*] --> Connecting
  Connecting --> Buffering: socket open
  Buffering --> Snapshotting: buffer deltas
  Snapshotting --> Replaying: snapshot loaded
  Replaying --> Live: drop stale, apply rest
  Live --> Live: next seq, checksum ok
  Live --> Resync: gap or checksum mismatch
  Resync --> Buffering: clear book
  Live --> Connecting: socket closed

      The 7 days

      One lane per day, one branch at a time

      Each day's branches merge into main in a fixed order. A branch rebases onto the newest main, passes CI, squash-merges, and only then does the next one go. Press Play to watch a day's lane, then open any branch card for its build steps.

        CI pipeline

        The checks grow with the project

        Every pull request runs these jobs before it can merge. Stages switch on as the days add them. Run the pipeline with a failing test to rehearse the loop: read the red job, push a fix to the same branch, run again.

          Branch protection on main

          • Pull request required for every change
          • Required checks: ci-python, ci-cpp, ci-web, integration
          • Linear history, squash merges only
          • 0 approvals needed: you are the whole team
          • Benchmarks report trends but never block a merge
          Merge-conflict playbook

          Design the repo so branches don't collide

          Even solo, branches collide when they edit the same lines of the same file. Most collisions come from a handful of shared files. Pick one to see the conflict it causes and how the plan avoids it.

          The daily git loop

          flowchart TD
  A[switch to main and pull] --> B[new branch dN/feature]
  B --> C[small commits, pre-commit hooks]
  C --> D[fetch and rebase on origin/main]
  D --> E[push and open PR]
  E --> F{CI green?}
  F -- no --> G[fix one red job on the branch]
  G --> E
  F -- yes --> H[squash-merge, delete branch]
  H --> I[next branch in the lane]
  I --> D

          Command cheat sheet

          # start a branch from a fresh main
git switch main
git pull --ff-only
git switch -c d2/kraken-adapter

# keep the next branch open while CI runs
git worktree add ../rtd-next -b d2/binance-adapter origin/main

# before pushing: replay your commits on the newest main
git fetch origin
git rebase origin/main
make check
git push -u origin HEAD

# open the PR and watch CI
gh pr create --fill
gh pr checks --watch

# merge when green, then clean up
gh pr merge --squash --delete-branch
git worktree remove ../rtd-next

# remember how you resolved a conflict, reuse it next rebase
git config --global rerere.enabled true

          If a day slips

          • Finish the lane in order; never merge past an unmerged branch.
          • Drop stretch items, then move the day's last branch to the front of the next session.
          • Never merge on red CI, and rebase any branch older than a day.
